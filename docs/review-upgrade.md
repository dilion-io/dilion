# 검토 수정 사항 배포 메모

## 런타임과 권한

- Go 1.26.8 이상을 사용한다. CI와 parity 빌드도 동일한 최소 패치로 맞췄다.
- Go 의존성을 갱신했고 CI의 독립 `govulncheck` job이 도달 가능한 취약점을 검사한다.
- 사용자 관리 API는 `service_role`·`supabase_admin` 역할 지정을 거부한다.
  사용자 정의 RLS 역할은 유지한다. 기존 잘못된 사용자 행도 로그인·refresh·OAuth
  사용자 토큰 발급 시 `authenticated`로 제한한다. 머신 서비스 키 발급은 별개다.
- 이미 유출된 service-role JWT는 이 변경만으로 무효화되지 않는다. 기존 사용자
  행의 예약 역할 부여 여부를 점검하고, 악용이 확인되면 서명 키 교체 및 노출된
  자격증명 폐기를 별도 사고 대응 절차로 진행한다.

## 동의 스케줄 마이그레이션

`0202_consent_state.sql`은 append-only 원장에서 현재 동의 상태를 backfill하고
재확인 예정일 인덱스를 추가한다. 원장은 계속 근거 기록이며, 읽기 API의 정책
해석은 즉시 반영된다.

구버전은 새 projection을 갱신하지 않으므로 **기존 쓰기 서버와 worker를 모두
중지한 뒤 마이그레이션하고 신버전을 시작한다**. 구버전과의 혼합 쓰기 배포는
지원하지 않는다. 큰 원장의 최초 backfill은 유지보수 시간과 DB 여유 공간을
사전에 측정한다.

새 동의의 예정일은 같은 트랜잭션에서 기록한다. backfill·정책 변경 후 재계산은
`retention-batch-size`만큼 keyset 순회하며 점진 반영된다. 사용자 수가 많으면
전체 순회에 여러 scanner tick이 필요하다. 예정일이 된 항목만 배치에 포함하고,
동시 scanner는 잠금을 획득한 경우에만 알림과 outbox를 함께 기록한다.
보존 유예 중인 키와 이미 파기된 동의 키가 뒤의 대상 처리를 가로막지 않는다.

## 프로필과 삭제

프로필은 암복호화 중 DB 연결을 점유하지 않는다. 저장 시 원본 ciphertext를
재확인하고 동시 변경이면 재시도한다. 삭제 요청 생성과 최종 저장은 동일한
트랜잭션 잠금으로 순서를 정한다. 삭제 진행·완료 또는 키 파기를 확인하면
늦게 도착한 쓰기를 거부한다. 매우 높은 동일 사용자 경합에서는 409 응답을
받은 클라이언트가 backoff 후 patch를 재시도할 수 있다.

## 기능 지원표

GitHub Actions의 parity summary가 default/flagged 실행별로 operationId와
“구현됨·부분 호환·미구현·미검증”을 자동 생성한다. 테스트 성공 경로와 실제
차이·실패·중단 여부가 판정 근거다. 오류 응답만 일치한 항목은 구현 보증으로
취급하지 않는다. 자세한 재현 방법은 [parity README](../test/parity/README.md)를
참고한다.
